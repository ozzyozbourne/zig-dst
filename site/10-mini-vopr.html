Mini-VOPR: a whole cluster in one seed

Every piece from the earlier examples, wired the way TigerBeetle's VOPR wires it. One seed picks the "weather" (a swarm of fault settings), then drives a 3- or 5-replica Viewstamped Replication cluster through crashes, lost unsynced writes, packet loss, duplication, reordering and partitions. Checkers run on every commit. A second liveness phase then heals a core and requires convergence within 5,000 ticks. Every trace below is parsed from a real run of examples/10-mini-vopr/main.zig.

01The simulator: one seed feeds everything

The real code under test is the VSR protocol (prepare, prepare_ok, commit, view change, repair) and the transfer state machine. Everything around it is simulated and driven by one PRNG: time is a u64 tick, the network is a list of packets with delivery ticks, and the disk is a durable WAL plus a FIFO queue of unsynced writes. Note the second PRNG: options_swarm draws the knobs first, then the simulator gets DefaultPrng.init(random.int(u64)), so adding a knob later does not reshuffle every fault decision.

02Two phases: safety, then liveness with a core

Safety phase: every fault is on. It ends when every client request has a reply, or after 3,000 ticks without a reply. Liveness phase: pick a random core (a quorum or more; every replica if the safety phase stalled), restart down core replicas, heal the network inside the core, cut the rest off permanently, stop crashes. The core must then converge (same view, a primary inside the core, commit = log head = canonical head, same state hash) within 5,000 ticks. "Eventually" is not testable; "within N ticks" is. 03The VSR message flow, from real packets

These are not schematic arrows. Each arrow is a packet from the --events output: it leaves at its send tick and lands at its delivery tick, which is why the arrows slant by different amounts (random delay). The violet bars are WAL writes, from the tick the write was issued to the tick it became durable. A backup's prepare_ok always starts after its bar ends: a backup may vouch only for what is on disk. 05The two planted bugs, and the exact failing step

    

      

        
Bug 1 · --bug-commit-early

        
main.zig, Simulator.try_commit. The correct rule needs a replication quorum of durable copies.


fn try_commit(sim: *Simulator, r: u8) void {
    const rep = &sim.replicas[r];
    // BUG --bug-commit-early: one durable copy (the primary's own) is treated as enough.
    // In a calm cluster every backup acks a moment later anyway, so no test notices.
    const needed: u8 = if (bug_commit_early) 1 else sim.quorum();
    while (rep.commit < rep.log.items.len) {
        const op = rep.commit + 1;
        var count: u8 = 0;
        for (rep.acked[0..sim.n()]) |a| count += @intFromBool(a >= op);
        if (count < needed) break;
        sim.commit_one(r);
    }
}

// Choose the log with the highest (log_view, op). Any replication quorum intersects this

var commit_max: u32 = 0;
for (rep.dvcs[0..sim.n()], 0..) |dvc, i| {

What the real VOPR has that this one does notStorage faults (corrupt or misdirected
      sectors, torn writes) and protocol-aware recovery, standbys, client eviction, upgrades between releases, replica pauses, the LSM forest,
      and an AOF validated at the end. The structure is the same: swarm the options, tick everything from one PRNG, check on every commit, then
      prove liveness on a healed core.
