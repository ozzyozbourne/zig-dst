What DST can't catch

A simulator finds the bugs that live inside its fault model, checked by its oracles. Everything outside those two boundaries is invisible to it. This chapter maps the boundaries, shows real evidence of where the model and reality differ, and places DST next to the tools that cover what it misses.

01The fault model is the boundary

DST tests your code against a model of everything underneath it. Click a layer.

02What the simulators in this guide model — and don't

Every example models a few failure modes in detail. The empty cells are bugs these simulators can't find, no matter how many seeds run. Rows marked not modeled anywhere are real-world failures none of the 14 examples simulate.

The model needs maintenance too.When production sees a failure the simulator never produced (a disk that returns success and drops the write, a clock that jumps backwards), the fix has two parts: the code fix and a new fault in the simulator, so the whole class is searched from then on.

03Reality check: real timers are messier than the model

The capture for example 02 ran a real sleep(5 ms) 300 times on this orb and recorded the actual elapsed time with a nanosecond monotonic clock. A simulator says "the timer fires at tick N". Reality says this:

A simulator can draw delays from a distribution like this, but only if someone measured it and put it in. Timing-sensitive behavior — throughput, tail latency, timeouts tuned too tight for a real network — is a question for benchmarks and production telemetry, not for DST.

Example 07's first draft defined "correct" backup reads as the backup has caught up to what this client has seen. That's session consistency, not linearizability: another client can still read stale data. The checker would have blessed a real bug. It became the planted bug instead.

🚨 False alarms

Example 09 with the fault atlas turned off injects faults on every copy of a block. Correct code then "fails" (no good copy left; Unrepairable). Those failures aren't bugs — the scenario is unrecoverable by design. The simulator has to only produce faults the system is supposed to survive.

🎲 Hidden nondeterminism

Example 06 hashed a struct with uninitialized padding bytes into its trace, so two identical runs printed different trace hashes. The program was deterministic; the determinism check wasn't.

Defense: test the tester.Every example in this guide ships a planted bug and checks that the sweep finds it. If a refactor of the simulator or the checker makes a planted bug stop failing, the harness got weaker. Examples 05, 08 and 10 also verified their liveness checks by breaking the code on purpose and confirming the check fired.

05Seeds are not regression tests

A seed means "this sequence of PRNG draws". Change the code so it draws one more random number and seed 3 is a different world. Durable regressions are pinned as hand-written scenarios — TigerBeetle keeps them in src/vsr/replica_test.zig. Example 14 demonstrates this for real, and the debugging chapter shows the workflow.

07The short version

DST is the best tool forlogic bugs in how your code reacts to faults and interleavings: consensus, recovery, retries, exactly-once delivery, caches, schedulers. It searches millions of scenarios and makes every failure replayable.
DST is blind tofaults outside its model, bugs below the interfaces it replaces (kernel, file system, firmware, drivers, libraries that do their own IO), performance, configuration and operator mistakes, and anything its oracles don't check.
