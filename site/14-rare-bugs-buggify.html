Rare bugs & BUGGIFY

A batching writer with retries, running over a simulated disk and network. It has three error paths that rarely run. Its bug needs two of them, in order, on the same flush: a short write, then a timeout on the retry. At realistic fault rates a plain random search needs tens to hundreds of thousands of seeds to find it. FoundationDB-style BUGGIFY points in the production code find the same bug in tens of seeds. Then we fix the bug and find that the failing seed no longer means anything, so we pin it as a hand-written scenario.

05The bug: one missing line, read by one rare path

Short-write handling in writer_on_ack

// Rare path 1: a short write. Retry the rest of the batch.
sim.hit(.short_write_retry);
sim.event(.short_ack, m.id, written, flush.count);
flush.count -= written;
// THE BUG: the offset is not advanced. The retry below does not notice (it sends from
// `base`); only the timeout path in writer_tick reads flush.offset.
if (!bug_stale_offset) flush.offset += written;
flush.after_short = true;
flush.id = sim.next_id;
sim.next_id += 1;
sim.send_request(sim.base, .retry);

The only reader of flush.offset: the timeout in writer_tick

if (sim.flush) |*flush| {
    if (sim.tick < flush.deadline) return;
    // Rare path 2: the timeout fires while the flush is still in progress.
    sim.hit(.timeout_in_flush);
    if (flush.after_short) sim.hit(.short_retry_then_timeout);
    sim.event(.timeout, flush.id, 0, 0);
    flush.id = sim.next_id;
    sim.next_id += 1;
    // Resend the flush we are waiting on, to the offset recorded in it.
    sim.send_request(flush.offset, .resend);
    return;
}
Why tests miss it

The BUGGIFY macro of this example

/// `if (sim.buggify(.point))` is this example's BUGGIFY macro. Off unless --buggify; then
/// true with probability 1/4 at points that are active for this seed.
fn buggify(sim: *Sim, point: Point) bool {
    if (!buggify_enabled or !sim.active[@backingInt(point)]) return false;
    if (sim.bug_prng.random().uintLessThan(u32, 4) != 0) return false;
    sim.fired[@backingInt(point)] += 1;
    sim.event(.buggify, @backingInt(point), 0, 0);
    return true;
}
// in the server's write path (production code):
if (n == m.count and m.count > 1 and sim.buggify(.short_write)) {
    n = sim.bug_prng.random().intRangeAtMost(u8, 1, m.count - 1);
}
// when arming the flush timeout:
const timeout: u64 = if (sim.buggify(.tiny_timeout)) timeout_ticks_buggified else timeout_ticks;

The fix: pin the failure as a scenario with no PRNG

The scenario mode replays a fixed list of steps against the same production code. Every delay is 1 tick and every fault is named. This follows the tests in TigerBeetle's src/vsr/replica_test.zig.

The scenario (from main.zig)

const scenario_name = "short-write-then-timeout";
const scenario = [_]Step{
    .{ .append = 4 },
    .{ .short_write_next = 2 },
    .{ .run = 3 },
    .{ .drop_acks = 1 },
    .{ .run = 20 },
    .{ .expect_durable = 4 },
};

Swarm testing draws the environment's fault rates per seed, so some seeds are far more hostile than production and rare environment events become common there. It does not reach rare branches that depend on the code's own knobs (a 2-tick timeout, a one-batch buffer). BUGGIFY reaches those.

FoundationDB · BUGGIFY

if (BUGGIFY) bufferSize = 1;
if ( randomize && BUGGIFY ) DD_SHARD_METRICS_TIMEOUT = 0.1;

Fault points written into the production code that are true only in simulation. On first evaluation each line is enabled or disabled for the whole run (25%). An enabled line evaluates to true 25% of the time. BUGGIFY_WITH_PROB(x) sets a custom firing rate. See FoundationDB: Simulation and Testing and transactional.blog/simulation/buggify. TigerBeetle mentions it once, as a TODO in src/vsr/replica.zig: // TODO(Buggify): skip updating the JV, since it isn't required for correctness.

src/testing/storage.zig · write_sectors_finish

if (storage.prng.chance(storage.options.write_fault_probability)) {
    if (storage.pick_faulty_sector(write.zone, write.offset, write.buffer.len)) |sector| {
        storage.fault_sector(write.zone, sector);
    }
}

Storage faults are injected at the moment a write completes. The StorageFaultAtlas keeps them within what the cluster can repair. env_write_len in this example works the same way: when the disk finishes a write, it may report a short one.

09Run it yourself

$ cd examples/14-rare-bugs-buggify
$ zig run main.zig -- sweep                                          # 2,000,000 seeds, correct code
$ zig run main.zig -- sweep 2000000 --bug-stale-offset               # realistic fault rates
$ zig run main.zig -- sweep 2000000 --bug-stale-offset --buggify     # BUGGIFY points on
$ zig run main.zig -- sweep 5000000 --bug-stale-offset --start 1000000000000   # another search order
$ zig run main.zig -- run 290087 --bug-stale-offset
$ zig run main.zig -- run 290087 --bug-stale-offset --extra-draw   # same seed, one extra PRNG draw
$ zig run main.zig -- scenario --bug-stale-offset                    # the pinned regression test
$ site/tools/capture.sh 14                                         # regenerate every number on this page

Use ReleaseSafe (zig build-exe -OReleaseSafe main.zig) for the big sweeps. Debug mode gives the same trace hashes but runs much slower.
