MediumExample 06

Swarm testing & shrinking

A ring buffer forgets everything when it is resized while completely full. A uniform random mix of operations almost never fills the queue, so it never sees the bug. Swarm testing lets each seed choose its own lopsided mix, and it hits the bug at the 22nd seed. A deterministic shrinker then replays edited operation lists until the 1000-op failure becomes a 33-op reproduction a human can read. Everything below is parsed from real runs of examples/06-swarm-testing-and-shrinking/main.zig.

01One seed, one configuration

The seed drives a single DefaultPrng. gen_weights() first decides how many of the 5 operation kinds to enable (1..5), then which ones as a uniform random combination, and gives each enabled kind a weight in 1..100. After that come the initial capacity (32..64) and 1000 operations. The operations do not depend on the queue's state, which is what lets the shrinker cut them up later. Each operation is applied to the real RingQueue and to a dumb array Model, and check() compares the two after every op.

Swarm weights, seed by seed

Each column is one seed's mix, normalised to 100%. The column on the far right is the classic uniform mix (--no-swarm, every weight 1). Most swarm seeds are lopsided: whole kinds are switched off, and one kind dominates. Seed 21 is outlined.

02How deep does the queue get?

The bug needs a full queue, and the capacity is never below 32. Below is the deepest queue reached by each of seeds 0–499 running the correct code, with and without swarm (from per-seed.tsv). Under the uniform mix, pop and clear together make up 40% of operations, so the depth is a random walk that keeps getting pulled back to zero.

04The bug: full looks exactly like empty

The planted line in RingQueue.resize

fn resize(q: *RingQueue, new_cap: u32) bool {
    assert(new_cap >= cap_min and new_cap <= cap_max);
    if (new_cap < q.count) return false;
    const n = if (bug_enabled) (q.tail + q.cap - q.head) % q.cap
              else q.count;
    // Linearize into scratch (handles wrap-around), then copy back starting at 0.
    var scratch: [cap_max]u32 = undefined;
    for (0..n) |i| scratch[i] = q.get(@intCast(i));
    @memcpy(q.buf[0..n], scratch[0..n]);
    q.cap = new_cap;
    q.head = 0;
    q.count = n;
    q.tail = n % new_cap;
    return true;
}

Why ordinary tests miss it

(tail − head) mod cap is right for every count from 0 to cap−1. At count = cap, tail has wrapped all the way around to head, and the formula gives 0. Hitting it takes at least 32 net pushes with no clear, followed by a resize that is not rejected.

05The shrinker, round by round

shrink 21 --bug --ops logs every deletion it keeps, as indices into the original op list (logging only: the output is otherwise identical to plain shrink). The shrinker uses no randomness. It truncates after the failing op, deletes chunks of len/2, len/4, …, 1 while the failure still reproduces with the same kind (count_mismatch), then moves arguments toward their simplest values, and repeats until nothing changes.

Every VOPR seed draws its own cluster size, fault rates and workload, which is swarm testing at the level of the whole simulator.

Shrinking in TigerBeetle

There is no automatic shrinker under src/testing or in vopr.zig. Small reproductions come from two other places. One is VOPR CLI overrides (--requests-max, --packet-loss-ratio, --lite), which let a developer shrink a seed by hand. The other is src/testing/exhaustigen.zig, which lists small inputs in order, so the first failure it finds is already small.

09Run it yourself

$ cd examples/06-swarm-testing-and-shrinking
$ zig run -OReleaseSafe main.zig -- sweep 20000 --bug              # swarm: fails at seed 21
$ zig run -OReleaseSafe main.zig -- sweep 20000 --bug --no-swarm   # uniform mix: passes (misses the bug)
$ zig run -OReleaseSafe main.zig -- run 21 --bug --ops             # every op with head/tail/count/cap
$ zig run -OReleaseSafe main.zig -- shrink 21 --bug                # 1000 ops -> 33 ops
