Deterministic Simulation Testing

Run your real code inside a fake world — fake clock, fake network, fake disk, fake scheduler — where every event is chosen by one random seed. Throw faults at it, check invariants after every step, and when something breaks, the seed is the bug report.

This site visualizes what happens underneath. Every chart is built from real program output captured in this repo — nothing is mocked up.

01Three properties, all required

🧪 Simulation

Every source of nondeterminism — time, network, disk, thread scheduling, randomness — sits behind an interface. The test plugs in a simulated implementation that can inject faults on demand and advance time instantly.

🎯 Determinism

Same seed + same code ⇒ the exact same execution, byte for byte. A failure is one integer. It can never be "flaky, can't reproduce" — you replay it under a debugger.

✅ Testing

Invariants and oracles are checked continuously — after every step, message, or disk write — not just at the end. A bug is caught at the tick where it happens, not a million ticks later.

02The trick: swap the world, keep the code

Production code never calls clock_gettime, send(), or pwrite() directly. It talks to Time, MessageBus, and Storage interfaces. TigerBeetle literally makes the replica generic over them: ReplicaType(StateMachine, MessageBus, Storage, AOF). Toggle the world below.

04Two phases: safety, then liveness

Faults can legitimately stop progress (a partitioned cluster should refuse to commit). So a simulator like the VOPR splits the run: first check that nothing wrong happens under faults; then heal a core of nodes and check that everything eventually happens. This shape appears in examples 05, 08, 09, and 10, and in src/vopr.zig as transition_to_liveness_mode(core).

SAFETY PHASE · faults on · loss, dup, partitions, crashes, corruption
assert: no divergence, no lost acks, conservation
LIVENESS · heal core
assert: converges in ≤ N ticks

Safety violations look like

two leaders in one term · op N committed with two different checksums · an acked write lost after a crash · money not conserved · corrupt bytes returned to a client

Liveness violations look like

a healthy quorum that never elects a leader · a client whose retry is never answered · replicas that never converge · a block that can't be repaired even though a good copy exists

08Determinism killers (and how the examples avoid them)

⏰
Wall clock

Any now() makes runs differ. Inject Time; advance a tick counter (ex 02, TimeSim in src/stdx/time.zig).

🧵
OS threads

The kernel picks interleavings. Use one event loop or explicit state-machine tasks with a seeded scheduler (ex 03). TigerBeetle is single-threaded by design.

🎲
Hidden randomness

One PRNG per run, everything derived from it — including sub-seeds for network and storage (options_swarm).

🗺️
Unordered iteration

Hash maps keyed by pointers, or randomized iteration (Go maps), reorder events. Iterate in index order.

🧱
Uninitialized bytes

Hashing a struct with padding gave example 06 different trace hashes for identical runs until it hashed a [3]u64 instead. Real bug caught while building this guide.

🌐
Real IO

Sockets and files have their own timing. Replace them with a packet simulator (ex 05) and in-memory storage (ex 04, 09).

09Where DST helps — and where it doesn't

Strong fitconsensus & replication · storage engines and WALs · crash recovery · exactly-once delivery · schedulers · caches with TTLs · any concurrent state machine
Weak fitcode bound to big nondeterministic platforms you can't stub (GPU drivers, browsers) · performance measurement (a simulator models latency, it doesn't measure it) · retrofitting a codebase that calls the clock and spawns threads everywhere

Language matters less than architecture. Zig, C, C++ (FoundationDB) and Rust (madsim, turmoil) make it natural; JS/TS and Python work through a custom event loop; Go and the JVM fight you because the runtime owns scheduling — unless you use a deterministic hypervisor like Antithesis.
