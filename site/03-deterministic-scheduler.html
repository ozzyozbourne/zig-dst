A deterministic scheduler

Threads are replaced by tasks written as explicit state machines, and the OS scheduler by one line: runnable[scheduler.uintLessThan(u8, runnable_count)]. The interleaving becomes a seeded random input. A lost update or a deadlock is then a seed number that replays tick for tick. Every trace, balance and rate on this page is parsed from captured runs of examples/03-deterministic-scheduler/main.zig.

01The world around the transfer code

The system under test is a bank transfer: lock → lock → read from → read to → write from → write to → unlock. The transfer logic, the lock protocol and the invariant checker are the real thing. Threads, mutexes, preemption and time are all simulated. One root seed gives two sub-seeds: one draws the workload (2–4 accounts at $100, 2–5 tasks, 1–3 transfers of $1–60 each), the other draws every scheduling decision.

02Underneath: program counters, shared memory, one pick per tick

Each Task holds a program counter pc: Pc. Its "locals" (seen_from, seen_to) live in the struct instead of on a stack, so they survive a yield. World.step(task) runs one atomic slice and moves pc along one arrow. Every arrow is a yield point, and World.check() runs after every tick. Choose a captured run and step through it.

Program counter of each task (the Pc enum). The yellow state is where the task will resume. Dimmed states are skipped by this design.

03The two planted bugs, in code and in a wait-for graph

--bug: skip locking

fn first_pc() Pc {
    // BUG (--bug): skip locking entirely.
    return if (bug_no_lock) .read_from else .lock_first;
}

Without locks the task goes straight to read_from. Then write_from stores seen_from - amount, a value computed from a read made one or more yields earlier. If another task wrote that account in between, its write is overwritten.

--bug-deadlock: locks in argument order

fn lock_order(task: *const Task) [2]u8 {
    const t = task.current();
    if (bug_deadlock) return .{ t.from, t.to };
    // Correct: a global order (lowest account first)
    // makes a wait-for cycle impossible.
    return .{ @min(t.from, t.to), @max(t.from, t.to) };
}

A task waiting on a held lock is simply not runnable (World.runnable). When nothing is runnable and some task is unfinished, the run fails with deadlock and prints the wait-for graph.

05Why a stress test with real threads rarely sees this

On real hardware a thread usually runs read → write in nanoseconds without being preempted. The bug needs a context switch, or a racing core, inside that window. How TigerBeetle does the same thing

    
TigerBeetle doesn't need a fake thread scheduler. Its real code is already built like this example: one thread, async submissions with callbacks, and
      long operations written as explicit stage machines.

src/testing/io.zig · IO.run()


/// Pass all queued submissions to the kernel and peek for completions.
pub fn run(io: *IO) !void {
    while (io.completed.pop()) |completion| {
        completion.callback(io, completion);
    }
}

        
Callbacks are the yield points, and completed is the run queue. In src/testing/storage.zig,
          Storage.step() (line 361) completes the next read or write by its ready_at time, drawn from the seeded PRNG
          (read_latency() / write_latency()). src/testing/cluster.zig Cluster.tick() and
          src/vopr.zig Simulator.tick() drive it all from stdx.PRNG.from_seed(seed).
