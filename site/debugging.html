Debugging a failing seed

A sweep prints FAIL at seed=3. This chapter walks from that line to the root cause, a fix, and a regression test that survives the fix. It uses the real output of example 10, the mini-VOPR, run with the planted --bug-commit-early bug. The checker fires at the end of the run, but the wrong decision happened much earlier. The work is to walk back from the symptom to that decision. Every log line, tick and hash below is parsed from files captured by site/tools/captures/debug.sh.

1Reproduce: the replay must be boringstage 1 / 7

The sweep runs seeds 0, 1, 2, … and stops at the first failure. It prints the reason and the exact command to replay it. Before you read any log, check that the replay really is deterministic. Run it twice and compare the bytes, not only the verdict. If two runs differ, the simulator has a source of nondeterminism (wall clock, hash-map order, uninitialized padding). That is the first bug to fix, because nothing you learn from one run would carry over to the next.

4Hypothesis, then confirm itstage 4 / 7

Hypothesis: the primary commits an op before a replication quorum holds it durably. A falsifiable prediction follows from it: in the buggy run, canonical commits are made with fewer than quorum known copies, and in the correct run, never. The quorum condition is in try_commit:

buggy: what runs with --bug-commit-early
/// Primary: commit every op that a replication quorum holds durably.
fn try_commit(sim: *Simulator, r: u8) void {
    const rep = &sim.replicas[r];
    // BUG --bug-commit-early: one durable copy (the primary's own) is treated as enough.
    // In a calm cluster every backup acks a moment later anyway, so no test notices.
    const needed: u8 = if (bug_commit_early) 1 else sim.quorum();
    while (rep.commit < rep.log.items.len) {
        const op = rep.commit + 1;
        var count: u8 = 0;
        for (rep.acked[0..sim.n()]) |a| count += @intFromBool(a >= op);
        if (count < needed) break;   // needed == 1: own durable write suffices
        sim.commit_one(r);
    }
}
fixed: the same function without the flag
/// Primary: commit every op that a replication quorum holds durably.
fn try_commit(sim: *Simulator, r: u8) void {
    const rep = &sim.replicas[r];


    const needed: u8 = sim.quorum(); // replica_count / 2 + 1
    while (rep.commit < rep.log.items.len) {
        const op = rep.commit + 1;
        var count: u8 = 0;
        for (rep.acked[0..sim.n()]) |a| count += @intFromBool(a >= op);
        if (count < needed) break;   // own write + prepare_oks >= majority
        sim.commit_one(r);
    }
}

rep.acked[i] is set from the primary's own on_write_done and from each prepare_ok, so count is the "copies known" column above. fn quorum returns replica_count / 2 + 1.

TigerBeetle states the same rule in src/vsr/replica.zig on_prepare_ok. The replication quorum is computed in src/vsr.zig quorums(), which asserts that it intersects the view-change quorum (assert(quorum_view_change + quorum_replication > replica_count)). That intersection is the property the bug breaks: a view-change quorum {R1, R2} that shares no replica with the "commit quorum" {R0}.

6Seed stability: why "seed 3" is not a regression teststage 6 / 7

The tempting regression test is "add run 3 to CI". It does not work. A seed reproduces a run only for the exact same code. The fix changes when the primary commits and replies. Every send draws loss, duplication and delay from the same simulator PRNG that also decides crashes and partitions. So from the first changed decision on, every later random draw lands somewhere else. Seed 3 under the fixed code runs in a different world:

How TigerBeetle pins a scenario

For scenarios that must keep being tested, TigerBeetle does not keep a seed. It writes the scenario down in src/vsr/replica_test.zig. The tests run the real replicas in the same simulated cluster. TestContext.init takes a fixed seed: u64 = 123 that only shapes background randomness such as delays. The faults are scripted with link filters (drop_all, drop, pass_all) and the outcome is asserted. t.run() ticks until the cluster stops making progress for 8,200 ticks. The scenario on this page, an isolated primary that must not commit, is already pinned:

// src/vsr/replica_test.zig
test "Cluster: network: partition 1-2 (isolate primary, symmetric)" {
    // The primary cannot communicate with either backup, but the backups can communicate with one
    // another. The backups will perform a view-change since they don't receive heartbeats.
    const t = try TestContext.init(.{ .replica_count = 3 });
    defer t.deinit();

    var c = t.clients(.{});
    try c.request(2, 2);

    const p = t.replica(.A0);
    p.drop_all(.B1, .bidirectional);
    p.drop_all(.B2, .bidirectional);
    try c.request(3, 3);
    try expectEqual(p.commit(), 2);   // the isolated primary must not commit op 3
}

The last line is exactly the invariant --bug-commit-early breaks: with that bug, the isolated A0 would commit op 3 alone. The test does not depend on a lucky seed. It survives refactors that change how many random numbers are drawn, because the scenario is in the code. Related pinned scenarios in the same file:

Note that our mini-VOPR has no scripted-fault API. Its faults come only from the PRNG. To pin this scenario here, you would add one, as in TigerBeetle's TestContext (an exercise; not done on this page).

7A debugging checklist, and how TigerBeetle developers do itstage 7 / 7

Checklist

  1. Reproduce twice, compare bytes. Same seed and same commit should give the same trace hash and identical logs. If not, stop and fix the nondeterminism first.
  2. Parse the failure message. Which checker, which tick, which replica, which op, and which other commit it disagrees with. The canonical side usually points at the earlier moment.
  3. Turn up the detail, not the noise. Use an opt-in, print-only flag (--events here, -Dvopr-log=full in TigerBeetle) that does not consume randomness, and check that the trace hash is unchanged.
  4. Walk backwards from the symptom. Find the first tick where state was already wrong: a commit that no quorum holds, a reply for an op that later vanishes. Zoom in on that window.
  5. Write the hypothesis as a falsifiable count. "Every canonical commit had ≥ quorum copies" can be checked on the buggy and on the fixed run.
  6. Fix, re-run the seed, then sweep everything. The seed confirms the fix; the sweep checks that it broke nothing else.
  7. Pin the scenario, not the seed. Write a scripted test (faults by hand, assertion on the invariant), because seeds reshuffle when the code changes.
  8. Check the checker. Re-enable the bug and confirm the sweep still catches it (here: ).

docs/internals/vopr.md: "Because our simulator is deterministic based on a seed number and the Git commit, we can perfectly reproduce any bugs discovered in testing for easy local debugging." A failure is reported as seed + commit, the same pair this page uses (seed 3, commit of main.zig).

  • -Dvopr-log=short prints only state transitions through Cluster.log_replica, whose columns are documented in docs/internals/testing.md ("VOPR Output"). The mini-VOPR status line imitates it.
  • src/vopr.zig CLIArgs has runtime overrides for narrowing a run without editing code: --ticks-max-requests, --ticks-max-convergence, --packet-loss-ratio, --requests-max, with the comment "Feel free to add more runtime overrides here!"
  • vopr.md: "we also test for specific cases that are hard or slow to replicate through random simulation", linking src/vsr/replica_test.zig, the pinned tests of stage 6.
