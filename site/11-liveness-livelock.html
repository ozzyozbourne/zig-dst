Liveness: the bug that never does anything wrong

15 of this guide's 16 planted bugs are safety bugs: something bad happens and an assertion fires. This page is about the other kind. A Raft-style cluster replicating a counter runs through partitions and crashes. Then the simulator heals a core quorum and waits. With --bug-fixed-timeout, terms climb forever and nobody wins an election. With --bug-no-retry-on-leader-change, one client waits forever for a request that no longer exists. In both runs no checker ever sees a wrong state. Catching these bugs takes a different checker (progress within a bound) and a different way of running the simulation (faults first, then heal).

01Safety → heal → liveness, and two verdicts per run

Each run has two phases, like TigerBeetle's VOPR. In the safety phase (ticks 0–2000) everything may fail: partitions, crashes, lost packets. Not making progress there is often correct, because with no quorum nothing should commit. At tick 2000, transition_to_liveness_mode picks a random core of at least a quorum, restarts it, heals every link inside it, and cuts the rest off for good. Then the liveness checker starts its clock: a stable leader and the commit of every pending request within 3000 ticks. The safety checkers keep running the whole time. Every run below therefore reports both outcomes.

03Why it never ends: timers re-armed by a shared event

Jitter in the network does not save a fixed timeout. In this simulator a node re-arms its election timer whenever it starts an election, grants a vote, or adopts a higher term, like etcd's becomeFollower. One candidate's RequestVote therefore re-arms every follower within one delivery window. That is a shared event. With equal timeouts, the next round fires in the same order with the same offsets, and so does every round after it. Each bar below runs from a timer's (re)arm to the point where it was reset or fired, reconstructed from the log: re-arms happen exactly at ?, >, v, and ^ events, and there are no heartbeats because there is no leader. A red bar fired and started an election. A grey bar was reset before it could fire.

The bug: one line in arm_election_timer

fn arm_election_timer(node: *Node, now: u64) void {
    const lo = election_timeout_mean - timeout_spread / 2;
    // THE BUG (--bug-fixed-timeout sets spread = 0): every node draws the same number, so
    // timers re-armed by the same event fire in the same order, at the same offsets, forever.
    node.election_deadline = now + node.prng.random().intRangeAtMost(u64, lo, lo + timeout_spread);
}
// correct: timeout_spread = 20  ->  uniform in [20, 40]
// buggy:   timeout_spread = 0   ->  always 30

The shared event: stepping down re-arms

/// Raft's universal rule: seeing a higher term makes you a follower in that term.
/// Like etcd's becomeFollower, stepping down also re-arms the election timer. That is a
/// SHARED EVENT: one broadcast of a higher term re-arms many timers in the same tick.
fn observe_term(sim: *Simulator, node: *Node, term: u64) void {
    if (term <= node.current_term) return;
    node.current_term = term;
    node.voted_for = none;
    node.role = .follower;
    node.leader = none;
    node.votes = 0;
    node.arm_election_timer(sim.tick);
    sim.event(node.id, '>');
}

04The second liveness bug: a request nobody retries

--bug-no-retry-on-leader-change is a different kind of liveness bug. The cluster is healthy and elects a stable leader soon after the heal, yet one client is stuck forever. Once a leader accepts a request (appends it to its log), the buggy client stops its retry timer. On seed 3 the client sends request #8 to node 1, which has been isolated by a partition and still believes it leads term 6. Node 1 accepts the request, but the term-7 leader's log wins and the entry is truncated. The checker's second clause, "every request committed", is what catches it. "A leader exists" is not enough.

Try it: one election after a shared re-arm (JS re-implementation)

Model: n nodes re-arm when a higher-term broadcast reaches them (delay 1–6 ticks). Each draws a timeout from [30−K/2, 30−K/2+K]. A node whose timer fires before the first RequestVote reaches it stands as a candidate. Other nodes vote for the first RequestVote they receive. With no majority, the round's RequestVotes become the next shared re-arm event. This is not the Zig code. Same seed, same run.

07Determinism: the livelock replays byte for byte

A liveness failure is a long run (5000 ticks, hundreds of events), and a different seed would be a different story. So it matters that the replay is exact. run 11 --bug-fixed-timeout and run 3 --bug-no-retry-on-leader-change were each captured twice. The page hashes both captures in your browser.

08How TigerBeetle does this

The structure is TigerBeetle's. src/vopr.zig runs the requests with every fault enabled, then calls transition_to_liveness_mode(core) and ticks until pending() is null, up to ticks_max_convergence. If the cluster does not converge, cluster_recoverable first rules out cores that could not possibly make progress. Only then does it report fatal(.liveness, "no state convergence: {s}", .{reason}).
