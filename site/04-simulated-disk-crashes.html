Simulated disk & crashes

The disk becomes a byte array with a volatile write cache in front of it. A write becomes durable only on fsync, or whenever the disk decides to write a sector back on its own. A crash keeps or drops each cached sector independently, so a three-sector WAL record can come back whole, vanish, or come back torn. Every sector, byte and count below is parsed from captured runs of examples/04-simulated-disk-crashes/main.zig.

01Real store, simulated disk

The WAL encoding, checksum, hash chain and recovery loop (Store.recover) are the code under test. The disk, time, fsync latency (1–6 ticks), background writeback (15 % per tick) and power loss (one in 80 per tick) are simulated. One DefaultPrng(seed) draws the workload and crash times, fills the disk with noise, and seeds the disk's own PRNG.

02A WAL record, byte by byte

From encode(): a 32-byte header followed by the value, zero-padded to a 64-byte sector boundary, so a record spans 1–3 sectors (value up to 160 bytes). The checksum is Wyhash(0x5eed, bytes[8 .. 32+len]). It covers the parent, seq, key, len and value, but not itself. The bytes below are the real header the recovery scan read at the first torn record of run 0. Hover a byte to see it.

/// On-disk layout (little endian):
///   [0..8)   checksum of bytes [8 .. 32+len)
///   [8..16)  parent: checksum of the previous record (hash chain; 0 for the first)
///   [16..24) seq
///   [24]     key   [25] len   [26..32) zero padding
///   [32..32+len) value, then zero padding to the sector boundary

06Why kill -9 tests don't find these bugs

    
kill -9 kills the process, not the machine. Bytes that write() accepted are already in the kernel page cache, and the kernel
      flushes them later whether or not the process is still alive. Only power loss, a kernel panic or a hypervisor kill throws the caches away, and only
      the device losing power partway through a multi-sector writeback can tear a record.
