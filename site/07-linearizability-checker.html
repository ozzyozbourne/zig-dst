Linearizability checker

With three concurrent clients there is no single "expected answer" to compare against. The oracle records a history of intervals (invoke → complete) and searches for any order of the operations that respects real time and is a legal run of a register. This page takes real histories from the Zig simulator, runs the same backtracking search step by step, and shows a bug that every per-operation check misses.

01The system under test and the simulated world

A primary executes writes, gives each one a version and replicates it asynchronously to a backup. Replication messages take 1–30 ticks and can arrive out of order, so the backup buffers them (backup_buffer) and applies them in version order. Clients read from either replica. The only difference between correct mode and --bug is how long the backup waits before it answers a read.

03Underneath the oracle: the Wing & Gong backtracking search

search(ops, done, state, memo) picks which op takes effect next. An op is a candidate only if no unplaced op completed before it was invoked. Placing a write sets the register. Placing a read is allowed only if the register holds the value the read returned. Each failed (done-set, state) pair is stored in a 4096×13-bit memo, so the search never explores the same future twice. The tree below is that search, run in JS on the real key history, in the same op order as main.zig.

Why it is impossible (seed 3)

R(x)=3 needs W1 < W3 < R3. R(x)=1 then needs a W1 placed after W3, but W1 completed (t=7) before either read began. Every branch of the tree ends at a read whose value the register does not hold at that point. Delta-debugging (minimize) dropped W(x:=2) because the contradiction does not need it. Removing any other op makes the history linearizable.

Why ordinary tests stay greenThese per-operation assertions in complete hold in both modes. Every answer is plausible on its own: read-your-writes, monotonic reads, and "the value really was committed at the version that served it". 
assert(version >= client.last_seen);
if (op.kind == .read) assert(value == sim.value_at(op.key, version));
Only the history-level check fails, because the failure needs two clients and a real-time relation between them.

Same seed, both modes: seed 3

With the bug, c0's backup read returns the stale 1 as soon as the backup has applied c0's own token (v1). In correct mode the same read waits for the read index and returns the value c1 had already seen. (Without the bug the run draws different random numbers after that point, because the extra read_index_request sends consume PRNG draws.)

08How TigerBeetle does this

TigerBeetle mostly avoids the search: VSR exposes the linearization, because every reply carries its op number. The tester puts replies back in op order and checks them against a sequential model in linear time.

src/testing/reply_sequence.zig

//! Replies from the cluster may arrive out-of-order; the ReplySequence reassembles them in the
//! correct order (by ascending op number).

        _ = context;
        return std.math.order(a.reply.header.op, b.reply.header.op);

Once the order is known, the Auditor's oracle is a sequential model again. check_state runs every tick for each replica and checks that each new commit matches or extends the canonical commit history. check_replicas in this example is the tiny version: the backup's log is always a prefix of the primary's.

When to search, when to checkIf the system can tell the tester its claimed order (op numbers, versions), check that order directly, in linear time. Use a Knossos-style search when the order is hidden, as here, where backup reads never get an op number.
