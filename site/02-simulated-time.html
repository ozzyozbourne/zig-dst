Simulated time

Never read the real clock. The TTL cache under test asks a Time interface what time it is. In production that interface wraps the OS clock. In the simulator it wraps TimeSim, a counter that moves only when the seeded simulator says so. Waiting 12 hours costs one addition, every replay sees the same timestamps, and the simulator can land time exactly on a deadline. That is where the planted >-instead-of->= bug lives. Every number below comes from real runs of examples/02-simulated-time/main.zig (Zig 0.17, ReleaseSafe).

01One interface, two clocks

The cache never calls the OS. It calls self.time.monotonic_ms(), a type-erased context plus a vtable, the same shape as TigerBeetle's stdx.Time. The same TtlCache code runs against either clock. The seed drives every decision in the simulator: which operation runs, which key, which TTL, and how far time jumps.

04How the simulator moves the clock

const Advance = enum { small, medium, jump, on_deadline, before_deadline };
// roll < 30: look at the MODEL, pick a live entry, land exactly on its deadline (roll < 20) or one tick before it.
if (deadline > now_ms + 1) {
    if (roll < 20) return .{ .on_deadline, deadline - now_ms };
    return .{ .before_deadline, deadline - 1 - now_ms };
}
return switch (roll % 10) {   // otherwise: blind random advances
    0...4 => .{ .small, random.intRangeAtMost(u64, 1, 10) },
    5...8 => .{ .medium, random.intRangeAtMost(u64, 1, 5 * ms_per_s) },
    else => .{ .jump, random.intRangeAtMost(u64, ms_per_hour, 12 * ms_per_hour) },
};

05Time compression

The program never times itself, because that would mean reading the wall clock. The capture script wraps each sweep in the shell's time instead. Press the button: the counter replays the 100,000-seed sweep at its real measured speed.

06Why a sleep()-based test misses the boundary

The capture script ran this test on the orb: put at t0 with a 5 ms TTL, time.sleep(5 ms), then get at t1. It repeated the test 300 times and read the monotonic clock in nanoseconds. The chart shows how far each get landed past the deadline.

Missing the boundary, or hitting it by luck, are both bad. With a nanosecond clock, as in TigerBeetle's Instant, the bug window is 1 ns wide, and no run lands in it. With a millisecond clock, whether get falls into the deadline's millisecond depends on where inside a millisecond put happened and how late the scheduler woke the thread. The result is a test that fails on some runs and passes on others, and never reproduces on demand. The usual "fix" is sleep(ttl + 10ms), which never tests the boundary again. A 6-hour TTL would need a 6-hour test. The simulator's on_deadline advance lands on the boundary deterministically, and seed 1 replays it every time.

src/vsr.zig · Timeout.fired

pub fn fired(self: *const Timeout) bool {
    if (self.ticking and self.ticks >= self.after_dynamic.?) {
        log.debug("{}: {s} fired", .{ self.id, self.name });
        if (self.ticks > self.after_dynamic.?) {
            log.err("{}: {s} is firing every tick", .{ self.id, self.name });
            @panic("timeout was not reset correctly");
        }
        return true;

Protocol timeouts count ticks and fire on >=, the same boundary this example protects. The > check panics if a timeout was not reset at the exact tick it fired.
