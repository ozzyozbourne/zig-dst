Inside TigerBeetle's VOPR

The VOPR runs TigerBeetle's real replica code, the same ReplicaType that ships in production, inside a simulated world made of an in-memory disk, a packet simulator and a tick-driven clock. A single 64-bit seed decides how many replicas there are, how lossy the network is, how slow and faulty every disk is and when replicas crash. Every chart, log line and hash on this page comes from zig-out/bin/vopr runs captured by site/tools/captures/tb.sh.

01Real replica, fake world

TigerBeetle's replica is a type function. vsr.ReplicaType takes the state machine, message bus, storage and AOF as comptime parameters. Production passes in io_uring-backed implementations. The simulator passes in deterministic fakes. No code path in the replica can tell the difference: it sees the same interfaces, and time arrives through a Time vtable that is either TimeOS or TimeSim.

02One seed grows a whole world

main turns the CLI seed into a PRNG with stdx.PRNG.from_seed (SplitMix64 expands it into a 256-bit Xoshiro256++ state). It then calls options_swarm(&prng), which draws every knob of the world in a fixed order, including three sub-seeds that give the cluster, the network and the storage their own independent PRNG streams. The main PRNG then keeps driving the simulator itself: request arrival, crashes, pauses and the choice of liveness core. Pick a seed: the values come from that seed's captured SEED= header.

03Inside one Simulator.tick

One tick is 10 ms of simulated time. A tick first drains everything that has become ready: it alternates network.step() (deliver one due packet per path) and storage.step() (finish one due read or write per replica) until neither advances, so I/O can complete faster than a tick. Then it advances the clocks, ticks every client and replica, runs the checkers, and finally lets the simulator inject requests, upgrades, crashes and pauses. Step through the real code:

04Every seed is a different world: the swarm

The VOPR does not test one configuration with many random events. It is a swarm: each seed first picks a configuration, then plays out events inside it. Some worlds have one replica and a perfect network, others six replicas, six standbys, 30% packet loss and disks with one-second writes. 07Who decides that a run is correct: the checkers

TigerBeetle runs with assertions enabled in production, and the simulator adds checkers that see the whole cluster at once. A failed assertion or checker exits with a Failure code, and the seed plus the commit reproduce it exactly.

StateChecker: one linear history

Runs on every .committed event and every tick for each up replica. Every replica's commit_min must walk the same hash chain: a new state's parent must be the checksum of the previous cluster commit, and a request may only be committed if a client actually has it in flight. Key lines are highlighted.

StorageChecker: byte-identical replicas

At every compaction bar and checkpoint, the checksum of all acquired grid blocks (and of the superblock checkpoint and the client replies) must equal what the first replica to reach that op recorded.

Network faults: submit_packet_finish

Every due packet passes through partition filters, random loss and random replay before delivery (src/testing/packet_simulator.zig).

Liveness: safety mode → liveness mode

Once all requests are done (or the tick budget runs out), the VOPR picks a core of replicas, heals them, and turns off every fault. The core must then converge (pending() == null). If it doesn't, cluster_recoverable decides whether that counts as a real liveness bug.

Where the disk may lie: storage fault zones

The simulated disk is one in-memory byte array split into the real vsr.Zone layout. Faults are only injected where a fully connected cluster can still recover. For the WAL, the client replies and the grid, ClusterFaultAtlas spreads faults so that each chunk is faulty on exactly quorum_replication − 1 replicas, which guarantees that a clean copy survives somewhere. 09Try it

$ cd tigerbeetle
$ ./zig/download.sh                         # the pinned Zig 0.16
$ ./zig/zig build vopr -Drelease             # build (ReleaseSafe) and run one random seed
$ ./zig/zig build vopr -Drelease -- 42       # seed 42 via the build step (CI passes the commit hash)
$ ./zig/zig build vopr:build -Drelease       # build only → ./zig-out/bin/vopr
$ ./zig-out/bin/vopr 42                      # the binary takes the seed directly, no "--"
$ ./zig-out/bin/vopr 42 2>&1 | sha256sum    # the log goes to stderr; same hash every time
$ timeout 300 ./zig-out/bin/vopr 1337        # some seeds need millions of ticks
$ site/tools/capture.sh tb                  # regenerate everything on this page
