A simulated network

A packet simulator stands in for the network. Every path holds a priority queue of in-flight messages keyed by the tick they become deliverable, and loss, duplication, reordering, full buffers and clogged links are all decisions drawn from one seed. On this network, a server with client sessions has to apply each transfer exactly once. Everything below is parsed from real runs of examples/05-simulated-network/main.zig.

01The world around the server

The code under test is Server.on_request (sessions and dedup) and the client's request, retry and reply logic. Everything between them is simulated: time is a tick counter, the network is a set of per-path heaps, and every fault, think time and amount comes from one master PRNG. That PRNG first draws how hostile this seed's network is, then derives a sub-seed for the network and one for each client.

This seed's SEED= block, as gauges

Each needle shows where the seed landed inside the range that run_seed() draws from. Seed 0 gets a lossy, fast network with 4 clients. Seed 1 gets a slow network with no loss and a long timeout.

02Underneath: the packet simulator

Network.submit() pushes a packet onto its path's heap with ready_at = now + max(delay_min, Exponential(delay_mean)) and a send sequence number that breaks ties. Each tick, Network.receive() pops every packet whose ready_at has passed, unless the path is clogged. Loss and replay are decided when a packet comes out of the queue, not when it goes in, which is the same place TigerBeetle decides them, in submit_packet_finish(). A replayed packet is delivered now, and a copy is pushed back with a fresh delay.

The delay distribution, with this seed's real parameters

Bars count the delay= of every packet sent during the safety phase of the real run. Dots show the exact distribution of max(min, ⌊Exp(mean)⌋). The floor comes from std.math.lossyCast, and every draw below the minimum gets clamped up to it. A random delay also reorders: two packets sent in order arrive out of order whenever the second one draws the shorter delay.

04The three-way duplicate decision

A client sends r+1 only after it has the reply to r, so a request that reaches the server is new (== session + 1), a repeat of the latest one (==), or older (<). The counts on the branches are how often each one fired in the real correct run of seed 0, with all faults on.

Correct: Server.on_request

if (message.request == session.request + 1) {
    const reply = server.apply(session, message);
    ...
    return reply;
}
// The client protocol (one request in flight) guarantees it never runs ahead.
assert(message.request <= session.request);
if (message.request == session.request) {
    ...
    return session.reply;
}
trace_event(9, message.client, message.request, session.request);
log(tick, "server: ignore old c{d} r{d} (session at r{d})", ...);
return null;

--bug-reply-stale keeps balances right and returns wrong replies instead. It needs a second client's transfer to land between the apply and the retry, and the checker catches it because it inspects every reply on the wire, including late duplicates that the client discards:

05Safety phase, heal, liveness phase

A network that drops every packet would pass every safety check. So after ticks_max_safety, the run calls transition_to_liveness_mode(), which sets delay to 1 tick and loss and replay to 0 but leaves clogging on, as TigerBeetle does. From then on, every client must get all its replies within 3000 ticks. Seed 1 is a good example: its clients are still mid-workload when the heal comes.

Loss and replay are decided at delivery time. The replay is a clone pushed back with a fresh delay.
